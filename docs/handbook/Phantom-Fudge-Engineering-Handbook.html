Reading map and current reality

TL;DR: Phantom Fudge is a Windows conversation companion with local speech recognition, not an invisible process and not yet an Azure question-answering product. Read this book as an explanation of boundaries: between presentation and capture, samples and text, a request and its completion, and a researched proposal and working software.

Overview: what this book is for

The original problem sounded like a small notepad: show private speaker notes while presenting. That problem expanded into a local transcription-first interface, selectable Computer/Mic/Both inputs, and a researched proposal for explicitly sending a question to an Azure model. The important engineering work is not drawing a rectangle. It is keeping each promise narrow enough to implement and each state transition strong enough to preserve data. The current product contract records those distinct requirements rather than collapsing them into a claim of universal invisibility (docs\PRODUCT.md:6-29).

This handbook is intended to support three activities. A new contributor should be able to run and navigate the application without guessing. A senior engineer should be able to review its invariants and tradeoffs. A future book editor should be able to assemble the chapters, figures, screenshots, glossary and development journal into a coherent narrative. The source chapters are Markdown; the generated HTML/PDF is an edition of those sources, not a separate authoritative implementation.

The implemented system in one page

The WPF application owns its native window and starts without an ordinary taskbar/Alt-Tab entry. Its startup path distinguishes synthetic diagnostics from normal single-instance operation, creates MainWindow, installs recovery callbacks, and calls ShowProtected (src\PhantomFudge.App\App.xaml.cs:13-58). The UI is not a browser or a remote webpage.

The speech path remains local. The native adapter selects explicit audio endpoints, while the Python server accepts one authenticated session and uses separate decoder state for declared sources. AudioSource names Computer and Microphone; those are input identities, not detected people (src\PhantomFudge.Core\AudioSource.cs:3-30). TranscriptBuffer preserves source-specific partials and labelled final lines (src\PhantomFudge.Core\TranscriptBuffer.cs:6-97).

The launch script can start/reuse the local Python service, but that is not permission to start audio capture. -NotesOnly avoids service startup, and an existing app is revealed without rebuilding it (scripts\Run-PhantomFudge.ps1:17-41). Docker recipes are a possible later deployment of the headless service, not the normal runtime dependency.

Principal engineer guide

TL;DR: The central insight is identity and completion must survive every asynchronous boundary. Source identity survives audio transport, request identity will survive future model streams, and completion means drained ownership rather than a convenient boolean. Presentation privacy is a separate, bounded contract; it cannot repair lifecycle mistakes.

Overview: the one idea

It is tempting to describe the application as "audio in, text out, hidden window." That description omits the information required to make it dependable. Computer and Mic can produce interleaved packets; recognizers revise hypotheses; Stop clears visible running state before all final text has drained; a hidden window still owns data; and an excluded HWND remains an ordinary operating-system object. Each boundary needs explicit identity and completion semantics.

The source enum assigns different wire identities to Computer and Microphone (src\PhantomFudge.Core\AudioSource.cs:3-22). The transcript store holds separate partials, but final IDs are session-global (src\PhantomFudge.Core\TranscriptBuffer.cs:9-18, src\PhantomFudge.Core\TranscriptBuffer.cs:48-72). The native adapter separately protects its lifecycle and invalidates queued starts when Stop is requested (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:71-152,182-189). These are concrete mechanisms, not an assumed generic event-driven architecture.

The insight in a different language

This Python-like pseudocode explains the C# contract; it is not a production implementation:

def on_packet(source, pcm):
    require(source in selected_sources)
    require(pcm_is_valid(pcm))
    if not queue.try_append(source, pcm):
        fault_entire_session("backpressure")  # do not silently lose a question

async def stop():
    state = STOPPING
    cancel_pending_start()
    await release_selected_inputs()
    await drain_accepted_audio_and_receive_source_finals()
    state = STOPPED

def begin_next_session():
    require(state == STOPPED)                 # not merely is_running == False
    preserve_unfinished_text()
    reset_session_global_final_id()

The application implements bounded queues and source-aware frames in TranscriptionSocket; the server validates each track and finalizes each declared decoder before its stopped event (src\PhantomFudge.App\Audio\TranscriptionSocket.cs:11-71, services\transcription\server.py:235-338). The pseudocode's "drain" is therefore a chain of ownership transitions, not a delay inserted to make a race less likely.

Review the dangerous boundaries first

Running is not completion

The native adapter can cease reporting Running while cleanup/final delivery continues. The UI must therefore block Start and destructive transcript actions during Stopping, not reset the final-ID counter as soon as a boolean flips. Otherwise an old final can arrive with a large ID after a new session starts, and a valid new final ID1 is rejected as a duplicate. The buffer's global-ID rule is correct only when its session boundary is correct (src\PhantomFudge.Core\TranscriptBuffer.cs:23-38,48-57).

Input identity is not speaker identity

Mic may capture the owner's voice, room sound, or speaker echo. Computer may include all output on a selected endpoint, not only the meeting. The correct labels are source names. Turning those labels into verified people would be a new, unsupported claim. The public contract states this boundary explicitly (docs\DUAL-SOURCE-AUDIO.md:8-26).

Privacy is not one boolean

Window exclusion, source authorization, local token checks, no automatic cloud upload, and unsaved-data behavior answer different questions. A protected window can still coexist with an OS microphone indicator. A successful local GDI fixture does not establish every Teams/Zoom/Meet/ OBS path. The qualification matrix keeps these observations separate (docs\QUALIFICATION.md:1-26).

A plan is not a runtime component

Azure Ask currently exists in design documents and TODOs. A principal-level diagram should not quietly insert an operational cloud box into the implemented path. The planned architecture requires immutable question snapshots, source-scoped commit and request-bound streaming; none is implied by the current text buffer (docs\AI-ANSWER-ARCHITECTURE.md:1-37).

Where to go deep

Start with the native lifecycle and transport when reviewing concurrency. Read the server's source state and worker loop when reviewing completeness. Read UI stop coordination and buffer mutation together when reviewing user data preservation. Read the capture policy beside its qualifications—not alone—when reviewing privacy language.

For a product decision, ask whether it changes data origin, lifetime, visibility, authority or completion. A new color mostly changes presentation. A new input changes all five. An Azure answer provider additionally crosses an egress and identity boundary.

Review exercise

Consider a user who selects Both, starts capture, hides the window during a slow final decode, then immediately asks to start again. Draw the ownership/state sequence. Identify where the native capture, socket, decoder, UI and buffer can legitimately disagree about "running." The correct design does not require those components to share one boolean; it requires that the coordinator not start a new logical session until the old completion boundary is satisfied.

Zero-to-hero learning path

TL;DR: Learn enough of each technology to trace one real packet and one real user action. Do not try to master all of Windows, C#, Python, networking and machine learning before opening the project. The learning path is a sequence of explanations and bounded exercises.

Overview: two languages, one product

The native project targets net10.0-windows, uses WPF and references the Core project plus NAudio (src\PhantomFudge.App\PhantomFudge.App.csproj:1-16). The Core project has no WPF dependency, which makes text/identity policies easier to test independently (src\PhantomFudge.Core\PhantomFudge.Core.csproj:1-5). Python hosts the local recognition service, with dependencies explicitly pinned (services\transcription\requirements.txt:1-20).

This is a technology boundary, not a competition between language quality. C# controls the Windows integration; Vosk's native model does recognition through Python bindings. The benchmark compares actual recognizers, not whether braces or indentation are better.

Part III: learn the byte arithmetic

The wire format is16,000 samples per second, one channel,16 bits per sample. Divide bits by eight to get bytes:16,000 x1 x2 =32,000 PCM bytes per second. A100ms payload is3,200 bytes. V2 adds one source byte per WebSocket message, not per audio sample. Thus a3,200-byte PCM payload becomes a3,201-byte message; it is not a WAV file and has no WAV header (docs\DUAL-SOURCE-AUDIO.md:37-53).

This arithmetic helps diagnose errors. An odd-length PCM payload is invalid because a16-bit sample needs two bytes. A source prefix belongs outside the PCM passed to the recognizer. Counting that prefix as sound would shift every subsequent sample boundary.

The phrase "two channels" can be misleading here. The application uses two independent mono source tracks, not one interleaved stereo stream. Each recognizer gets mono audio; the protocol carries source identity separately.

Part IV: asynchronous thinking

Compare a synchronous function with a lifecycle:

result = recognize(audio)       # one call; ownership is simple

start_requested = True
await service_ready()
open_inputs()
# callbacks and network events now arrive independently
await stop_requested()
await all_inputs_released()
await accepted_audio_drained()
await final_text_received()

An await does not mean "nothing else can happen." The WPF dispatcher can process another user action while an operation awaits I/O. Conversely, doing CPU recognition on an event loop can prevent other requests from being handled. The server therefore uses a bounded worker for native recognition, while native startup is kept away from a blocked WPF dispatcher (services\transcription\server.py:109-142, src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:106-124).

Three questions prevent many mistakes:

  1. Who owns this resource while the operation is incomplete?
  2. What identifies this result as belonging to the current source/session?
  3. What event proves completion, rather than merely intent to stop?

Part V: safe first exercises

Exercise 1: source labels, no devices

Read SourceTranscriptTests. Explain why a Computer final must leave a Mic partial visible. Then sketch a table of two partials, one Computer final, and one Mic final. This needs no microphone or backend (tests\PhantomFudge.Core.Tests\SourceTranscriptTests.cs:1-80).

Exercise 2: a rejected save

Read a test that changes a file outside the app, then attempts to save with an old fingerprint. Identify which version should survive. Do not use a real note as the experiment; the test creates an isolated directory (tests\PhantomFudge.Core.Tests\NoteFileStoreTests.cs:1-110).

Exercise 3: protocol without hardware

Run the native synthetic harness only after reading its entry mode. It uses fake transport/input objects for its normal test groups. The separate playback command is deliberately not part of the default suite (tests\PhantomFudge.Audio.Tests\Program.cs:18-71).

Exercise 4: a documentation-only screenshot

The documentation command renders actual WPF controls with synthetic text/device labels. It is not a Snipping Tool workaround for capturing someone else's private window (src\PhantomFudge.App\App.xaml.cs:31-36, scripts\Export-HandbookScreenshots.ps1:1-76).

How to avoid learning the wrong lesson

Do not conclude that a successful test suite proves hardware support, that the fastest batch recognizer has the lowest live partial latency, or that a private window is a security boundary. Those are different experiments. The repository deliberately leaves broader acceptance work open.

The glossary provides more than forty terms. Use it when a word becomes a blocker, then return to the code path. A good first contribution is a small test/documentation improvement that follows one real invariant end to end.

Product boundaries and decisions

TL;DR: Scope changes are not embarrassing historical debris; they are design inputs. The important discipline is to record what superseded what, update the affected contracts, and avoid treating an earlier assumption as a permanent requirement.

Overview: from a private notepad to a conversation companion

The initial request was a draggable speaker-notes window that would not appear in a screen share. The useful part of that request is implementable on supported Windows capture paths. The absolute version—no software can ever detect or record the surface—is not. The product contract therefore separates plain-text editing, movement, shell presentation, captured pixels, platform support and actual product qualification (docs\PRODUCT.md:6-29).

That separation made later changes tractable. Transcription became the main view. Notes became collapsible. The owner removed repetitive permission/rehearsal acknowledgments. Translucency became a real rendering requirement, rather than a hypothetical visual effect. A microphone track became explicitly requested after the original computer-only implementation. Finally, Azure answering became a researched future extension, not an automatic cloud replacement.

The development ledger records these changes as dated decisions and evidence, not a fictional linear plan that was correct from the beginning (TODO\16_DEVELOPMENT_LEDGER.todo:1-90). The public journal tells the fuller chronological story.

Architecture of a requirement

A requirement should identify its observable outcome and the evidence needed to claim it. For example, "no ordinary taskbar button" has a shell observation. "Computer audio becomes text" requires audio/protocol/recognizer evidence. "The recipient never sees the notes" needs the actual capture path; neither of the first two observations supplies it.

04 — Windows Capture, Cursors, and Focus

Overview: four questions, not one invisibility switch

A presentation aid has two audiences: the person reading its local window and the people receiving a captured presentation. Those audiences do not necessarily receive the same pixels. Phantom Fudge asks Windows to exclude its window from supported capture paths; it does not make the process nonexistent, encrypt the desktop, or control another program's recording implementation. WindowProtection.Configure performs a native configuration operation, not a recipient-side test. This distinction is the foundation of the feature, rather than a disclaimer added after it. (src\PhantomFudge.App\Native\WindowProtection.cs:18-46)

Question Mechanism or evidence

What does the audience actually receive? Independent recipient frames and recordings for that exact configuration

The qualification plan explicitly separates these dimensions. A successful API call cannot fill in the other three columns. Nor does a visible local Arrow establish that a recorder includes the pointer. (docs\QUALIFICATION.md:9-26; docs\CURSOR-AND-THEMES.md:21-37)

06 — Notes, Transcripts, and Explicit Storage

Overview: persistence is a deliberate boundary

Seeing text, retaining it in memory, and saving it are three different events. Phantom Fudge keeps one editable note and an in-memory transcript; neither is automatically a file. The note tracks its last successful saved value. The transcript tracks its last explicitly exported value. These distinctions let the UI warn about unsaved work without silently persisting meeting content. They also mean a crash can lose unexported text: the preview does not implement automatic recovery. (src\PhantomFudge.App\MainWindow.xaml.cs:22-30,267-283,384-391,753-760; docs\IMPLEMENTATION-STATUS.md:95-100,156-157)

Capture exclusion does not extend to a .txt file, the clipboard, a native file dialog, or process memory. File storage is therefore designed for bounded input and accidental-overwrite resistance, not advertised as a secure vault. Saving to a user-selected location is an explicit act with the ordinary privacy properties of that location. (src\PhantomFudge.App\MainWindow.xaml.cs:350,391; docs\PRODUCT.md:125-140)

Newcomer path: start with the transcript example, then follow Save. Principal-engineer path: inspect session-local ID reset, snapshot comparisons, byte bounds, and the remaining check-to-replace race. Chapter 11 explains why session reset must wait for final draining.

Notes use the WPF text editor as their current text surface. TranscriptBuffer separately owns accumulated final text and source-specific unfinished text. 7. Dual-input capture: two sources, one owned session

Why two inputs must not become one waveform

Imagine listening to computer playback while dictating a question into a microphone. Adding the samples together would discard the distinction the reader needs: which text came from playback, and which came from dictation? Phantom Fudge instead preserves two acquisition paths. WasapiInput selects render loopback for Computer and a capture endpoint for Microphone; each becomes a separate source-tagged stream. This is input attribution, not speaker identification. Several people can speak through Computer, and playback can acoustically reappear in Mic. The implementation contains no mixing or acoustic-echo-cancellation stage. (src\PhantomFudge.App\Audio\WasapiInput.cs:20-55, WasapiInput; docs\DUAL-SOURCE-AUDIO.md:8-23, “Design and boundaries”.)

The equally important distinction is selection versus capture. MainWindow defaults captureMode to Both, populates device lists, and subscribes to notifications; its constructor does not start recording. Start_Click checks the requested selections, protection readiness, and token before calling the transcriber. Merely launching the idle Python service is not permission to acquire audio. (src\PhantomFudge.App\MainWindow.xaml.cs:33-76, MainWindow; src\PhantomFudge.App\MainWindow.xaml.cs:589-625, Start_Click; scripts\Run-PhantomFudge.ps1:39-55, launcher.)

A callback, measured in bytes rather than intuition

Both WASAPI wrappers request shared-mode 16,000 Hz, 16-bit, mono PCM. Computer uses WasapiLoopbackCapture; Mic uses WasapiCapture. The wrapper documents NAudio's shared-capture conversion flags rather than implementing a custom application resampler. (src\PhantomFudge.App\Audio\WasapiInput.cs:48-54, constructor.)

The format yields:

  • 16,000 samples/second × 2 bytes/sample = 32,000 bytes/second per source.
  • A 100 ms silence frame contains 1,600 samples = 3,200 bytes.
  • A 48,000-byte callback represents 1.5 seconds of this PCM. OnAudio splits it into 32,000 and 16,000 bytes; the v2 transport adds a source byte to each, producing 32,001- and 16,001-byte binary messages.
  • Two live sources produce 64,000 PCM bytes/second before framing overhead—not a 32 kHz mixed track.

These are calculations from WaveFormat, the socket constants, and the callback chunking loop, not measured hardware callback sizes. (src\PhantomFudge.App\Audio\WasapiInput.cs:53-54, constructor; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:13-18, constants; src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:230-254, OnAudio; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:208-217, TryEnqueueAudio.)

OnAudio rejects invalid lengths, records packet arrival under that input's AudioGate, and enqueues copied chunks. Copying matters because a capture callback's buffer is reusable: the sender must not later observe a buffer that the capture implementation or caller has overwritten. A full transport budget faults the session rather than pretending the missing chunk was silence. (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:235-247, OnAudio; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:182-229, TryEnqueueAudio.)

Metering is throttled to approximately one update per 100 ms of callback time. Samples are read little-endian, divided by 32,768, squared, averaged, and square-rooted. Alternating +16,384 and −16,384 therefore yields RMS 0.5, not zero; opposite signs cancel in an arithmetic mean but not in energy. LevelAsync tests that exact distinction. (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:249-286, OnAudio, CalculateLevel; tests\PhantomFudge.Audio.Tests\Program.cs:202-209, LevelAsync.)

Silence cadence is transport continuity, not endpoint tuning

An idle track has its own 100 ms periodic timer. SilenceCadence.TrySchedule permits one silence frame only after at least 250 ms without a real packet and at least 100 ms since the previous synthetic frame. A real packet resets both timestamps. The shared per-input lock prevents a recent packet and silence decision from racing within that track. (src\PhantomFudge.App\Audio\SilenceCadence.cs:5-19, SilenceCadence; src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:289-314, SupplySilenceAsync.)

For example, after a packet at 1,000 ms, a decision at 1,249 ms fails; one at 1,250 ms may succeed. A delayed decision at 10,000 ms still emits only one 3,200-byte frame—it does not manufacture every missing interval. Timer scheduling can place the actual decision later than the threshold. Computer activity does not reset Mic's cadence, and vice versa. The corresponding synthetic tests check both the threshold and cross-source independence. (tests\PhantomFudge.Audio.Tests\Program.cs:212-225, SilenceCadenceAsync; tests\PhantomFudge.Audio.Tests\DualSourceTests.cs:498-519, DualInputPolicyAsync.)

Consequently, these timestamps describe callback arrival and supplied PCM, not acoustic onset measurements. Cadence does not change Vosk endpoint settings; its implementation only creates zero PCM. async def start(selection):
    observed_stop_version = atomic_read(stop_version)
    async with lifecycle:
        require_not_disposed()
        require_no_session_or_outstanding_release()
        inputs = validate(selection)
        with request_lock:
            if observed_stop_version != stop_version:
                raise StartupCanceled()
            session = reserve(inputs)
        await connect_and_validate_ready(session)
        await start_each_input_on_workers(session)

async def stop():
    with request_lock:
        increment_stop_version()
        request_current_session_stop()
    async with lifecycle:
        await finish_current_session()

8. Streaming protocol: preserving identity under backpressure

Why the protocol is more than a pipe

A socket that moves bytes successfully can still produce an incorrect transcript: it can mix sources, accumulate unbounded delay, accept replayed final IDs, or report completion before a decoder flushes. Phantom Fudge's protocol makes those boundaries explicit. The C# client owns admission and copied PCM; Python owns per-source decoding and publication; both reject invalid transitions rather than guessing how to recover. (src\PhantomFudge.App\Audio\TranscriptionSocket.cs:185-229, TryEnqueueAudio; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:389-468, ProcessMessage; services\transcription\server.py:225-348, Session.)

Compatibility is deliberately additive. Both speech versions use /v1/transcribe; v1 has unprefixed Computer PCM, while v2 declares a source subset and prefixes each binary message. The URL's v1 does not imply Computer-only operation. Management independently retains protocolVersion: 1 and advertises speechProtocolVersions: [1, 2]. (services\transcription\server.py:94-106, parse_start; services\transcription\server.py:179-193, runtime_info; services\transcription\server.py:255-262, Session.receive; services\transcription\server.py:446-449, routes.)

Admission before audio

TranscriptionSocket.ValidateEndpoint accepts only literal IPv4 or IPv6 loopback WebSocket URLs with the exact path. It rejects hostname resolution, user information, queries, fragments, escaped paths, and alternate numeric IP spellings. Proxies and redirects are disabled. The production native launcher uses IPv4 127.0.0.1; accepting [::1] in the client does not mean the default server binds IPv6. (src\PhantomFudge.App\Audio\TranscriptionSocket.cs:26-31, HTTP handler; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:73-89, ValidateEndpoint; services\transcription\manage.py:167-172, start.)

On the server, nonempty Origin headers are rejected, authentication requires exactly one Bearer header, and token comparison uses hmac.compare_digest. Query strings and request bodies are not accepted. Readiness and the single active-session gate are checked before upgrading. runtime.active = True occurs without an intervening await, so even a client stalled before its start message occupies the only admission slot. (services\transcription\server.py:171-176, authorized; services\transcription\server.py:353-378, transcribe.)

A frame calculation

AudioSource assigns byte 1 to Computer and 2 to Microphone. For 100 ms of 16 kHz mono PCM16, the payload is 16,000 × 0.1 × 2 = 3,200 bytes. V2 sends 1 + 3,200 = 3,201 application-message bytes. The first byte is metadata, not a sample; duration, queue bytes, and byte-rate credit count only the remaining PCM. WebSocket/TCP overhead is additional and is not included in this calculation. (src\PhantomFudge.Core\AudioSource.cs:3-7, AudioSource; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:13-17, constants; src\PhantomFudge.App\Audio\TranscriptionSocket.cs:208-217, TryEnqueueAudio; services\transcription\server.py:255-287, Session.receive.)

The smallest legal v2 message is three bytes: a source plus one two-byte sample. The largest is 32,001 bytes: a source plus one second of PCM. Legal message lengths are therefore odd, while legal PCM lengths are even. A prefix without PCM, an undeclared source, or 32,002 PCM bytes is invalid. (services\transcription\server.py:257-263, Session.receive; tests\PhantomFudge.Audio.Tests\DualSourceTests.cs:75-88, DrainV2Async.)

At 3,200 bytes per frame, twenty queued frames consume a source's full 64,000-byte budget: two seconds of audio. At two bytes per frame, the server's 32-frame cap wins after just 64 queued PCM bytes. Both limits are necessary: a byte-only rule permits many tiny objects, while a frame-only rule permits too much audio latency. A busy Computer stream cannot borrow Mic's unused source quota. The shared queue is FIFO, not a round-robin scheduler; “fairness” here means reserved admission budgets, not equal CPU time. (services\transcription\server.py:232-233, Session.__init__; services\transcription\server.py:277-287, Session.receive; services\transcription\tests\test_dual_protocol.py:461-497, source-budget tests.)

Translated from the C# admission algorithm:

def admit(source, pcm):
    validate_declared_source_and_even_nonempty_pcm(pcm)
    with queue_lock:
        if not accepting:
            return False
        if len(pcm) > 64000 - source_pending[source]:
            overflow = True
        elif len(pcm) > 128000 - total_pending:
            overflow = True
        else:
            frame = prefix_if_v2(source) + copy_bytes(pcm)
            reserve_pcm_budget(source, len(pcm))
            if try_write_channel(frame):
                submitted[source] += len(pcm)
                return True
            release_budget_and_clear_copy(frame)
            overflow = True
    if overflow:
        fault_entire_session()
    return False

Overflow is visible failure, not packet dropping or disk spill. The real method also handles closed/disposed state and per-version framing. (src\PhantomFudge.App\Audio\TranscriptionSocket.cs:185-229, TryEnqueueAudio.)

Rate is not backlog

Each server source separately starts with 64,000 byte credits and 200 frame credits, replenished at 32,000 bytes/second and 100 frames/second using monotonic elapsed time. Credits are capped at their burst sizes. Thus a source can spend an initial two-second byte burst, but sending 32,000 additional bytes immediately needs replenishment even if the decoder has emptied its queue. Conversely, a slow decoder can trigger backlog at an otherwise valid live rate. (services\transcription\server.py:42-56, Limits; services\transcription\server.py:212-222, SourceState; services\transcription\server.py:265-280, Session.receive.)

Other defaults are a five-second start-message wait, fifteen-second receive-idle wait, five-second decoder-operation wait, two-second send wait, and eight hours of submitted PCM duration per source. These are not advertised latency targets. (services\transcription\server.py:43-56, Limits; services\transcription\server.py:275-276, duration enforcement.)

Transcript clocks: global order, local time

Consider three emitted finals: Computer ID 1 at 0.0–0.2, Mic ID 2 at 0.0–0.1, then Computer ID 3 at 0.2–0.3. This is legal. IDs order session publication; timestamps order only the corresponding source's PCM. Comparing Mic's 0.1 against Computer's previous 0.2 would falsely reject valid interleaving. Session.publish keeps one global counter and a last_end per source. (services\transcription\server.py:212-235, state; services\transcription\server.py:289-315, publish; services\transcription\tests\test_dual_protocol.py:182-200, interleaved-final test.)

The server requires finite, nonnegative, nonregressing source times bounded by that source's received duration. V2 has no pre-rounding duration tolerance. Millisecond rounding is then clipped to whole elapsed milliseconds: 18 bytes represent 18 / 32,000 = 0.0005625 seconds, but cannot become a 0.001-second wire endpoint, so the result is 0.000. 9. Python recognition: shared model, independent histories

Why separate the model from its history?

Two sources need separate recognition histories, not two independently loaded copies of the same model. Computer playback must not become the acoustic context for a dictated Mic question. VoskFactory therefore retains one model and creates a new VoskRecognizer for each requested source. Each wrapper constructs its own KaldiRecognizer and maintains its own sample counter, offset, and last final endpoint. The shared model is treated as immutable by this application; mutable decoder state belongs to one source. (services\transcription\recognizer.py:41-67, VoskFactory, VoskRecognizer; services\transcription\server.py:378-386, transcribe.)

This distinction also explains the concurrency design. A single executor worker runs source-decoder operations away from aiohttp's event loop. The sources are logically independent but do not decode simultaneously on separate executor threads. That is a bounded-resource tradeoff, not a claim of equal per-source latency or proof that native libraries never use internal threads. The native manager additionally sets OPENBLAS_NUM_THREADS and OMP_NUM_THREADS to one. (services\transcription\server.py:109-142, Runtime; services\transcription\manage.py:167-176, start.)

Following one 100 ms frame

At 16,000 Hz and two bytes per mono sample, 3,200 bytes represent 1,600 samples and 0.1 seconds. Session.recognize dequeues a (source, pcm) pair, releases its queue accounting, and invokes only that source's decoder.accept through Runtime.cpu. This separates backpressure accounting from recognition progress: total received bytes can include queued work, while VoskRecognizer._samples advances only as frames reach the decoder. (services\transcription\server.py:274-287, Session.receive; services\transcription\server.py:317-333, Session.recognize; services\transcription\recognizer.py:82-84, VoskRecognizer.accept.)

accept increments _samples by len(pcm) // 2, calls AcceptWaveform, and branches on endpoint completion and the 30-second history boundary. A normal incomplete result uses PartialResult()["partial"]; an endpoint-complete result uses Result() and _final. Every new decoder enables word results with SetWords(True) and disables partial-word results with SetPartialWords(False). The application needs final word times, but exposes partial text rather than partial word alignments. (services\transcription\recognizer.py:64-96, decoder methods.)

Recognition is a small immutable result carrier: text, final flag, start, and end. It does not carry source identity; the enclosing Session already knows which source's decoder ran and adds the label during publication. Keeping these responsibilities separate lets recognizer tests focus on timing without needing a WebSocket. Partials are replacements, not append-only sentences

The server stores last_partial independently for each source and sends only changed partial text. A final resets that source's partial memory to None; it does not reset the other track. An empty initial partial can be emitted because "" differs from None. This is useful state information, not evidence of recognized speech. (services\transcription\server.py:212-220, SourceState; services\transcription\server.py:301-315, Session.publish.)

Final publication validates the result type, string type, 8,192-character service text limit, finite timestamps, and source-duration ordering before assigning the next global segment ID. These checks protect the wire contract even when a decoder adapter is replaced by a test double or returns invalid data. A final is committed recognition output, not a guarantee that the words are correct. (services\transcription\server.py:289-315, Session.publish; services\transcription\tests\test_dual_protocol.py:349-377, invalid-result and timestamp-regression tests.)

Bounding continuous-speech history

A stream need not pause conveniently. The wrapper therefore finalizes and recreates its mutable decoder once supplied audio since _offset reaches at least 30 seconds. This is a processed-audio threshold, not a wall-clock timer and not a configurable silence detector. The rollover check follows AcceptWaveform, so a frame that crosses the boundary is entirely consumed before rotation. (services\transcription\recognizer.py:82-93, VoskRecognizer.accept.)

Thirty seconds contains 30 × 16,000 = 480,000 samples, or 960,000 PCM bytes per source. These are cumulative processed bytes, not bytes retained in the server queue. If the existing decoder ended an utterance, rotation uses Result(); otherwise it forces FinalResult(). The wrapper then sets _offset to cumulative elapsed audio and creates a fresh decoder against the same model. (services\transcription\recognizer.py:83-90, accept; services\transcription\server.py:43-47, queue limits.)

The following JavaScript-shaped pseudocode translates the Python recognition branch:

function accept(pcm) {
  samples += Math.floor(pcm.length / 2);
  const complete = decoder.AcceptWaveform(pcm);
  const elapsed = samples / 16000;

  if (elapsed - offset >= 30) {
    const result = toFinal(
      complete ? decoder.Result() : decoder.FinalResult()
    );
    offset = elapsed;
    decoder = newDecoder(sharedModel, 16000);
    return result;
  }
  if (complete) return toFinal(decoder.Result());
  return { text: JSON.parse(decoder.PartialResult()).partial ?? "",
           final: false };
}

This is explanatory pseudocode, not an additional runtime or language port. toFinal represents the timestamp normalization performed by Python's _final. (services\transcription\recognizer.py:69-96, VoskRecognizer methods.)

Provisioning without hidden repair

Initialization creates a token only if one is absent, using 32 cryptographically random bytes rendered as lowercase hexadecimal. Serializing the launcher without trusting process names

lifecycle_lock is Windows-specific. It opens a workspace lock file, ensures at least one byte exists, and repeatedly attempts a nonblocking msvcrt lock on that byte. The acquisition deadline is 50 seconds with 100 ms polling. Start, Stop, and Status share this lock, so competing manager invocations cannot simultaneously rewrite the ownership receipt. This serializes cooperating managers for the workspace; it is not an operating-system-wide monopoly on the port. (services\transcription\manage.py:65-90, lifecycle_lock; services\transcription\manage.py:147-150, start; services\transcription\manage.py:203-222, stop, status.)

11 — State Machines and Failure Containment

Overview: a Boolean cannot describe a shutdown

“Running” answers whether a session is currently considered active. It does not answer whether a device has released its capture thread, whether queued audio has reached the recognizer, whether final text has returned, or whether a new session may safely reuse the UI's transcript IDs. Phantom Fudge's most important lifecycle rule is therefore:

IsRunning == false does not mean fully stopped, drained, and reusable.

Session.RequestStop immediately sets Running=false; StopSessionAsync and transport disposal still have substantial work afterward. The UI separately holds audioStopping through its awaited Stop path. A documented review found and fixed a stop/restart race by preserving this distinction. (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:29,363-423,504-518; src\PhantomFudge.App\MainWindow.xaml.cs:681-708; docs\IMPLEMENTATION-STATUS.md:23-25)

Newcomer path: follow the normal Stop sequence before reading the locks. Principal-engineer path: inspect queued-start invalidation, ownership after driver timeouts, and the difference between graceful drain and fault abort. The diagrams below name conceptual states; the production code implements them through fields, tasks, locks, and guards, not one central state enum.

Implementation: concurrency tools serve different purposes

Serialization does not cancel queued intent

SemaphoreSlim _lifecycle serializes asynchronous Start/Stop/Dispose bodies. But a semaphore alone would allow a Start already waiting behind another operation to run after Stop. The controller therefore captures _stopVersion before waiting, increments that version in RequestStop, and compares it under _requestLock before publishing a new session. A queued stale Start is rejected rather than resurrecting recording. (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:71-91,155-189)

After connection acceptance, each selected input starts on a worker task. Running becomes true only when every requested input started, no stop/failure is recorded, and no input already reported RecordingStopped. Thus Both is all-requested-inputs behavior, not “start whichever device happened to succeed.” (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:98-132)

The first fault wins

SignalFault uses Interlocked.CompareExchange to store one safe failure message. Subsequent simultaneous faults return early. It disables audio admission flags, clears Running, requests cancellation, aborts transport, and schedules serialized cleanup. The cleanup checks that its session is still the controller's current session. (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:338-360)

The code explicitly avoids acquiring another input's AudioGate while processing a callback failure. Otherwise two failing sources could each hold one gate and wait for the other. Per-input volatile admission flags and transport admission close the path without cross-track lock acquisition. This is a concrete deadlock-avoidance choice, not a reason to remove all synchronization. (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:235-246,338-349)

The socket budgets two seconds of PCM per source: 64,000 bytes at 16 kHz, mono, 16-bit; total pending PCM is capped at 128,000 bytes. A queue overflow faults the session rather than silently dropping frames and continuing a success-shaped transcript. Released frame arrays are cleared, but this is not a secure-erasure guarantee for every memory copy or crash dump. (src\PhantomFudge.App\Audio\TranscriptionSocket.cs:13-18,182-229,543-550; docs\QUALIFICATION.md:137-138)

Endpoint validation restricts the transport to literal loopback, and the HTTP handler disables proxies and redirects. 12. Performance and Benchmarks

Why a fast decoder is not necessarily a responsive application

Performance starts with a question, not a stopwatch. “How quickly can this engine decode a complete recording?” differs from “When does the presenter see a useful partial?” An engine can process a finished file faster than its duration yet wait too long before showing live text. The repository deliberately separates unpaced file decoding from a small paced-delivery experiment; neither measures the complete capture-to-WPF path. (tools\SpeechBench\bench.py:207-230, worker.decode; docs\SPEECH-BENCHMARK.md:88-118, “Speed and live-update limits”.)

This chapter analyzes existing evidence, not a newly executed benchmark. The public synthetic receipt records 32 cases, 164.070 seconds of audio, two serial warm passes, and 292 normalized reference words per pass. Repeating a recording improves timing observations; it does not create another independent speaker or double the accuracy sample. (tools\SpeechBench\results\synthetic-20261008.json:13-22, experiment metadata; tools\SpeechBench\results\synthetic-20261008.json:65-109, summary; tools\SpeechBench\bench.py:354-369, run.)

The comparison is also not C# versus Python. SAPI, Vosk, and Whisper are different recognition engines with different models and exposed APIs. C# hosts the installed Windows dictation engine; Python hosts Vosk and faster-whisper. Language-host differences are confounded with engine differences, so the experiment cannot isolate language overhead. (tools\SpeechBench\SapiBridge.cs:113-145, Recognize; tools\SpeechBench\bench.py:188-255, worker; docs\SPEECH-BENCHMARK.md:10-15, engine-versus-language distinction.)

The scoring algorithm

Normalize before aligning

normalize applies Unicode NFKC, lowercases, expands %, converts numeric strings through English cardinal words, removes apostrophes, and extracts alphabetic tokens. It does not drop stop words or repair one engine's terminology after seeing its output. Consequently, the benchmark ignores capitalization and punctuation but retains many genuine lexical errors. (tools\SpeechBench\metrics.py:8-25, NORMALIZATION, normalize.)

Normalization is a measurement policy, not semantic interpretation. 9:30 becomes two cardinals, while 9.30 uses decimal “point” wording; these can describe a similar intended time but score differently. Conversely, “don't” and “dont” become identical tokens. The tests make several such choices executable rather than leaving readers to infer them. (tools\SpeechBench\test_metrics.py:7-17, test_numbers_are_common, test_apostrophes; docs\SPEECH-BENCHMARK.md:74-77, numeric-format limitation.)

Levenshtein alignment and ties

For reference prefix length i and hypothesis prefix length j, the dynamic-programming table stores (total edits, substitutions, deletions, insertions). Equal tokens inherit the diagonal cell. Unequal tokens compare substitution, deletion, and insertion candidates, each costing one additional edit. When totals tie, candidate order prefers substitution, then deletion, then insertion. This stabilizes the reported S/D/I breakdown without making the alignment a semantic explanation of the recognizer's mistake. (tools\SpeechBench\metrics.py:28-55, errors.)

The table contains (reference length + 1) × (hypothesis length + 1) cells; thus this implementation's time and storage grow with their product. That is acceptable for the short fixture sentences, but a future long-recording evaluator should account for the matrix explicitly rather than assuming a streaming metric. This complexity follows directly from the allocation and nested loops. (tools\SpeechBench\metrics.py:31-48, errors.)

Corpus WER is:

WER = sum(substitutions + deletions + insertions)
      / sum(normalized reference words)

Do not average sentence percentages: one error in a one-word sentence should not outweigh one error in a much longer sentence simply because each sentence gets equal weight. An empty reference produces undefined WER; an empty hypothesis produces deletions. WER can exceed 100%, so 100 − WER is not a general “accuracy percentage.” (tools\SpeechBench\metrics.py:49-62, errors, aggregate; tools\SpeechBench\test_metrics.py:24-37, empty-input and weighted-aggregation tests.)

receipt = read_public_synthetic_receipt()

    rows = engine["rows"]
    summary = receipt["summary"][name]
    require_unique_pairs(rows, keys=("id", "repeat"))
    require_complete_case_repeat_grid(rows, receipt["cases"],
                                      receipt["repeats"])
    first_pass = [row for row in rows if row["repeat"] == 0]
    expected_errors = sum(row["substitutions"] + row["deletions"]
                          + row["insertions"] for row in first_pass)
    expected_words = sum(row["reference_words"] for row in first_pass)
    assert summary["wer"] == expected_errors / expected_words
    pass_times = [sum(r["decode_seconds"] for r in rows if r["repeat"] == k)
                  for k in range(receipt["repeats"])]
    assert summary["median_decode_seconds"] == median(pass_times)
# No capture, synthesis, download, or inference is necessary for this audit.

Failure outcomes belong in the experiment

An unavailable engine is not an infinitely slow engine, a zero-error engine, or a reason to install a new component silently. The SAPI bridge records unavailable status when no en-US recognizer exists; subprocess failures likewise produce an unavailable result rather than a fabricated timing row. A comparison report must retain that outcome and explain which configurations actually ran. (tools\SpeechBench\SapiBridge.cs:113-121, Recognize; tools\SpeechBench\bench.py:328-353, run.)

Inputs also have a contract: the loader rejects duplicate IDs and empty corpora, and the WAV reader requires uncompressed 16 kHz mono signed 16-bit PCM. Silent resampling would move preprocessing work and change the experiment without an explicit decision. Empty reference strings are technically accepted, but their undefined WER makes them inappropriate for ordinary accuracy ranking. These are methodological limits to document, not inconveniences to bypass. 13. Proposed Azure Answer Flow

Why question selection is the architectural center

Everything concerning QuestionDraft, Ask, source commit, Azure inference, and answer rendering in this chapter is PLANNED, not implemented. The existing research is complete as a design deliverable; the draft, commit, connection, client, and UI workstreams remain unstarted. No cloud integration or Azure performance result is implied by the diagrams or pseudocode. (TODO\27_AI_ANSWER_RESEARCH.todo:29-36, completion evidence; TODO\28_QUESTION_DRAFTS.todo:3-5, status; TODO\31_STREAMING_ANSWER_CLIENT.todo:30-36, completion evidence; TODO\32_ANSWER_UI_LIFECYCLE.todo:30-36, completion evidence.)

The hard problem is not posting text to a model. It is knowing which text the user intended to send, keeping that text stable during asynchronous recognition, and associating every answer with the right question. A microphone may contain earlier conversation; Computer audio may continue while a question is dictated. Treating the entire transcript as a prompt silently changes the product's data boundary. The proposed solution is an explicit editable draft followed by an immutable snapshot at Ask. (docs\AI-ANSWER-ARCHITECTURE.md:44-68, deliberate submission paths; docs\AI-ANSWER-PRIVACY.md:6-20, proposed default.)

A useful mental model has three objects: the transcript is an evolving observation, the draft is the user's working selection, and the snapshot is the exact outbound request content. They are related, but none should substitute for another. In particular, a better late recognition result must not rewrite a question already submitted. (docs\AI-ANSWER-ARCHITECTURE.md:84-122, planned local records and revision rules.)

Architecture: local speech, explicit text egress

The baseline preserves native Python ASR and adds a direct asynchronous C# answer provider. Sending through the Python speech service merely because it exists would add coupling and another hop without a demonstrated requirement. Authentication, request identity, and WPF updates belong with the desktop coordinator; model network work does not belong in capture callbacks or the recognizer CPU worker. (docs\AI-ANSWER-ARCHITECTURE.md:8-38, recommended baseline.)

Worked pseudocode: retries without duplicate finalization

This sketch specifies invariants for a future implementation, not methods currently callable in the service:

def process_commit(marker, session):
    key = (session.capture_id, marker.source, marker.request_id)
    prior = session.completed_commits.get(key)
    if prior is not None:
        require(prior.parameters == marker.parameters)
        return prior.ack             # no second final or epoch increment

    track = session.sources[marker.source]
    require(marker.epoch == track.epoch)
    require(track.processed_samples == marker.through_sample)
    final = track.finalize_and_replace_preserving_offset()
    final_ref = session.record_final(final)   # including an empty final
    old_epoch = track.epoch
    track.epoch += 1
    ack = Ack(key, old_epoch, track.epoch,
              marker.through_sample, final_ref)
    session.remember_bounded_commit(key, marker.parameters, ack)
    return ack

Lookup precedes current-epoch validation so a genuine retry can replay its original acknowledgment after the epoch has advanced. Changed parameters under the same request ID must fail. The eventual implementation also needs a defined publication/failure boundary and bounded deduplication lifetime; the sketch does not promise durable exactly-once delivery across process crashes. (docs\AI-ANSWER-ARCHITECTURE.md:146-158, commit ordering/idempotency; TODO\29_QUESTION_COMMIT_LATENCY.todo:26-28, duplicate/empty-commit acceptance.)

An armed question needs a start boundary as well as an end. Otherwise earlier Mic conversation enters the question. Current partials disable word-level timing, so arbitrary retrospective acoustic cuts cannot be reconstructed exactly from displayed text. A click watermark also covers delivered samples, not audio still inside a device buffer. A bounded tail-drain policy must be specified and measured rather than disguised as sample-exact knowledge of when the user finished speaking. (services\transcription\recognizer.py:64-67, _new_decoder; docs\AI-ANSWER-ARCHITECTURE.md:160-166, start and device-buffer boundaries.)

The initial provider would call Azure OpenAI v1 Responses with stream:true, store:false, background:false, no tools, no conversation ID, and no previous_response_id. Its model field identifies the approved deployment alias. “Foreground” describes API execution, not activating the desktop window. The exact SDK must be pinned and compile-checked; research examples are not an installed client. Question, answer, connection, audio, and capture-protection states must remain separate. Every streamed event would carry a request identity and sequence; stale events from A must never append to B. HTTP 200 or stream closure is not completion. Interrupted output stays visibly incomplete, and cancellation does not guarantee stopped remote billing. (docs\AI-ANSWER-ARCHITECTURE.md:168-207, state machines; docs\AI-ANSWER-ARCHITECTURE.md:238-252, streaming failures.)

The pane would remain inside the protected WPF surface. However, the existing TogglePresentationAsync hides the window and stops transcription before changing modes. Reusing it for draft correction would violate continuous Computer transcription. The future editor therefore needs a deliberate, separately tested focus transition—not an undocumented change to global mode semantics. Tradeoffs and adversarial event ordering

Consider an ordinary scheduling race rather than a network attack: the user asks A, cancels it, and asks B; a previously queued A delta then reaches the dispatcher. Disposing the HTTP stream is insufficient because the callback may already exist. The UI must compare the delta's request identity with the current answer generation before appending it. A cancellation acknowledgment and a stale-output guard solve different problems. (docs\AI-ANSWER-ARCHITECTURE.md:185-207, answer state and event rules; TODO\32_ANSWER_UI_LIFECYCLE.todo:19-25, delayed callbacks.)

Likewise, user edits during Mic finalization must remain authoritative for their own draft revision. The final acknowledgment can make a finalized alternative available, but cannot overwrite intervening edits or secretly submit it. Immediate Ask favors speed and visible user control; Finish dictation favors acknowledged recognition coverage. Neither path universally dominates, which is why the plan exposes both instead of hiding a heuristic choice behind one button. (docs\AI-ANSWER-ARCHITECTURE.md:58-68, submission paths; docs\AI-ANSWER-ARCHITECTURE.md:155-166, epochs and boundaries.)

Finally, bounded storage is a correctness decision: transcript eviction, commit-cache eviction, and answer truncation cannot be treated identically. Selected question text needs a retained copy; commit deduplication needs an explicit lifetime; oversized input or output needs a visible policy rather than silent alteration. Each limit should be exercised with synthetic boundary cases before the first authorized model request. (docs\AI-ANSWER-ARCHITECTURE.md:119-122, memory/input limits; docs\AI-ANSWER-ARCHITECTURE.md:155-156, bounded deduplication; TODO\31_STREAMING_ANSWER_CLIENT.todo:19-28, adapter bounds and tests.)

14. Answer Latency, Identity, and Privacy

Why these concerns belong together

The answer pipeline is PLANNED. No Azure endpoint, sign-in, model entitlement, retention configuration, or cloud latency was verified while writing this chapter. Its service contracts come from the repository's existing research, not fresh retrieval. Connection and latency workstreams explicitly report no implementation or execution evidence. (TODO\30_AZURE_ANSWER_CONNECTION.todo:31-37, completion evidence; TODO\33_ANSWER_LATENCY_QUALITY.todo:30-36, completion evidence; docs\AI-ANSWER-PRIVACY.md:133-151, primary-reference scope.)

Latency, identity, and privacy interact in practical ways. A surprise sign-in window delays the answer and introduces an external surface not covered by the application's capture policy. Sending the whole transcript makes request content harder to review and violates selected-text scope. Retrying a partial answer may duplicate disclosure and spending while making the UI look continuous. The proposed design therefore optimizes a useful answer to an explicitly frozen question, not merely an early network byte. (docs\AI-ANSWER-PRIVACY.md:27-40, authentication flow; docs\AI-ANSWER-PRIVACY.md:112-131, application safeguards; docs\AI-ANSWER-EVALUATION.md:30-40, user-visible metrics.)

The baseline keeps ASR local and adds text egress only at explicit Ask. Optional cloud audio requires a separate decision; good text-model performance cannot authorize uploading microphone or Computer PCM. (docs\AI-ANSWER-PRIVACY.md:6-20, proposed default; TODO\36_OPTIONAL_AZURE_SPEECH.todo:13-25, separate cloud-audio gate.)

A duration is meaningful only when both endpoints are defined. async def ask_reviewed_text(draft, profile):
    q0 = monotonic()
    snapshot = freeze_exact_displayed_revision(draft)
    request_id = random_id()
    credential = await silent_token_or_inline_signin_required(profile)
    request = bind_request(request_id, snapshot, profile)
    n1 = monotonic()
    first_delta = None
    first_render = None
    terminal = "incomplete"
    async for event in provider.stream(request, credential):
        if not active_request_matches(request_id, event.request_id):
            continue
        require_monotonic_sequence(event)
        if event.is_nonempty_text:
            first_delta = first_delta or monotonic()
            await renderer.append_bounded_batch(event.text)
            first_render = first_render or monotonic()
        if event.is_terminal:
            terminal = event.safe_terminal_code
    emit_metadata(request_id, terminal,
                  api_ttft=elapsed_or_missing(n1, first_delta),
                  ask_to_render=elapsed_or_missing(q0, first_render))

Tradeoffs: optimize the critical path without hiding failures

UI batching trades a small bounded rendering delay for avoiding a dispatcher operation per tiny delta. The proposed 16–50 ms interval is therefore a tuning range, not permission to accumulate an unbounded queue. Both bytes waiting and time without progress need limits; HTTP activity that never yields useful text should not keep an answer apparently alive forever. (docs\AI-ANSWER-ARCHITECTURE.md:240-249, batching and deadlines; docs\AI-ANSWER-EVALUATION.md:54-59, no-progress policy.)

A broker can enforce central quotas or private routing, but adds another authentication and streaming hop. It should be chosen for a demonstrated governance requirement, not assumed faster. If APIM enters that path, response buffering and body diagnostics become explicit review items because they can defeat streaming or export content. The direct path remains the initial proposal; no infrastructure was provisioned to test either option here. A useful test is tied to an invariant. "The app launches" would not have caught a late final poisoning the next session's IDs. A source-partial test that proves one track's final leaves the other pending text intact is much stronger for that specific requirement (tests\PhantomFudge.Core.Tests\SourceTranscriptTests.cs:1-80).

Working on a shared Windows desktop

An agent or test must not kill a running user's app to overwrite a locked executable. Build to an isolated output directory or create a new candidate. The native lifecycle script refuses to touch a preexisting PhantomFudge process and tracks only the processes it starts (scripts\Test-NativeLifecycle.ps1:16-22, :69-113).

Avoid parallel .NET commands that write the same project obj tree. Parallel research or independent Python checks are fine; two builds of the same Core project can race on generated cache files even when they use different final output directories. Compile once, then use --no-build where appropriate for follow-up checks.

The documentation fixture must never use real notes or chat content. It has its own command line path and validates a synthetic/no-recording result before copying images (src\PhantomFudge.App\App.xaml.cs:24-36, scripts\Export-HandbookScreenshots.ps1:1-76). A screenshot request is not authorization to capture a meeting or disable display affinity.

Failure tests worth keeping

The native harness covers authentication, framing, cancellation, bounded queues and delayed shutdown. Its entry point reports named groups and returns failure on a failing group (tests\PhantomFudge.Audio.Tests\Program.cs:18-71). Tests must also cover the interaction between layers: a fake device can fail after another input has started, or a final can arrive while UI Stop is still awaiting cleanup.

Python tests use injected recognizers for deterministic failure cases, while separate real-model fixtures prove that the production decoder can recognize generated speech. A fake recognizer is appropriate for protocol determinism, not evidence of speech accuracy. Conversely, one recognized synthetic sentence does not prove every cancellation path.

Interpreting results

Record source identity, environment, exact command, pass/failure, sample size and limitations. The implementation-status document is a bounded receipt, not a badge that everything is safe (docs\IMPLEMENTATION-STATUS.md:1-70).

For capture, an in-process RenderTargetBitmap image proves UI appearance. A cropped GDI fixture proves only the sampled local path. Neither proves what a remote participant sees. Run an intentionally unprotected positive control only outside a live presentation; it is supposed to be capturable.

Troubleshooting by symptom

The window is missing

First distinguish Hidden, minimized, failed initialization and a different running instance. Ctrl+Alt+Space and relaunch recovery are intended paths. The single-instance pipe accepts one fixed recovery command under current-user restrictions, not arbitrary scripts or filenames (src\PhantomFudge.App\Native\SingleInstance.cs:18-75).

If protection setup fails, the app withholds content and records a generic local notice rather than displaying an unprotected branded error window (src\PhantomFudge.App\LocalFailureNotice.cs:1-30). That notice is diagnostic data, not saved notes.

Start fails

Check the selected input mode, every requested device, local token, model and service version. In Both mode, a missing microphone must not silently become Computer-only. The native adapter validates selection and waits for protocol readiness before opening inputs (src\PhantomFudge.App\Audio\LoopbackTranscriber.cs:71-152).

Nothing is transcribed

A selected playback endpoint may not be the meeting application's actual output. A microphone may be muted or denied by Windows policy. A zero meter and an empty transcript are not enough to diagnose the same problem. Do not "fix" either by opening a different device automatically. Actual hardware diagnosis needs explicit user authorization and the named device configuration.

Stop seems slow

The application may be releasing native inputs, draining accepted audio or waiting for final recognition. IsRunning is not a complete shutdown contract. A hung native call cannot be safely treated as disposed merely because a UI timeout expired. The source retains ownership and blocks unsafe restart rather than using a success-shaped fallback.

Docker is missing

Normal native operation does not require it. Docker recipes are optional final-stage packaging. Only an explicit Docker mode should require a Docker engine (scripts\Start-Transcription.ps1:1-35). Do not turn a portability task back into a mandatory infrastructure dependency.

Release discipline

Keep candidate names/hashes immutable. If source, runtime, rendering or protocol changes, create a new candidate and rerun the affected evidence. Signed versus unsigned status must be explicit; signing does not guarantee SmartScreen or organizational acceptance.

The handbook and journal are now part of that discipline. A release that changes what the user sees needs current screenshots; a protocol change needs a current sequence diagram and source references. Freshness tooling detects changed inputs, but semantic review remains the author's job.

Privacy and assurance

TL;DR: The application can control its own inputs, storage, windows and requests. It cannot turn those controls into a universal guarantee about another recorder, the operating system, an administrator, a camera or a person. Assurance requires both a mechanism and the right experiment for the claim.

Overview: separate the questions

"Private" can mean that notes are absent from a recipient's frames, audio stays local, a token is not logged, a file is encrypted, or a process is not listed. Those are different properties. The current product explicitly does not promise process invisibility or a security/DRM boundary (docs\PRODUCT.md:125-140).

The first useful threat-model step is therefore to state what is controlled. The app owns its HWND and can request display affinity. It owns the selected capture objects and can require explicit Start. It owns the local protocol and can authenticate it. It does not own a meeting application's cursor-inclusion setting, the Windows microphone indicator or a camera aimed at the display.

Raw audio is handled as bounded in-memory frames. The test harness uses synthetic PCM and must not implicitly open real devices. This is a meaningful policy, but it is not a claim of secure memory erasure, immunity to dumps, or control over host swap/administrators.

Local service authentication

The server uses a bounded local token, constant-time comparison, a one-active-session admission rule and explicit frame limits. Management operations additionally match an instance identity; they are not arbitrary process-control APIs (services\transcription\server.py:65-176, services\transcription\manage.py:112-144).

A malicious process running as the same user or an administrator is not contained by calling the service "localhost." The token and current-user boundaries reduce accidental/cross-context access; they do not transform the workstation into a trusted enclave. The service itself does not open microphones or read chats; the C# client owns the selected device operations.

Storage boundaries

Notes and transcripts are not automatically persisted in the current preview. Explicit file saves are bounded UTF-8 operations with conflict checks and same-directory replacement (src\PhantomFudge.Core\NoteFileStore.cs:16-91). Ordinary file deletion does not establish secure erasure from SSDs, backups or snapshots. An unsaved warning prevents one kind of data loss, not every crash.

Do not log note hashes as a supposedly harmless substitute for text. A short predictable question can be dictionary-tested against a hash. Use random correlation IDs and counts where diagnostics need identity without content.

18. Extending the System

Why a small feature can require a wide review

An extension is safe when its responsibilities are narrow and its consequences are traced completely. Adding a source is not just another selector; it affects byte framing, queue budgets, timestamp validation, stop behavior, display provenance, tests, and privacy wording. Adding a theme is not just changing a background; selection, disabled controls, alpha composition, and capture qualification also matter. The architecture explicitly prefers small testable interfaces over a generic plugin framework. (docs\ARCHITECTURE.md:35-54, component responsibilities; src\PhantomFudge.Core\AudioSource.cs:3-30, source identity; src\PhantomFudge.App\ThemeBrushes.cs:9-31, semantic resources.)

This chapter teaches change analysis. It does not add a source, backend, provider, state field, or runtime capability. The Azure answer extension remains planned; its workstreams are useful examples of how to separate local state, protocol evolution, authorized integration, and final qualification. (TODO\28_QUESTION_DRAFTS.todo:13-20, local state tasks; TODO\29_QUESTION_COMMIT_LATENCY.todo:13-22, protocol tasks; TODO\30_AZURE_ANSWER_CONNECTION.todo:13-22, integration prerequisites.)

Begin at the recognition contract, not the model download. The service requires a Recognition object, bounded text, finite ordered times, and final results at stop.   • Can independent source decoders share immutable model weights without sharing recognition history?

5. Speech v1/v2 messages and bytes

{"type":"start","sampleRate":16000,"channels":1,"encoding":"pcm_s16le"}

8. Errors and recovery interpretation

Why evidence needs its own architecture

A living engineering book must distinguish what exists, what was observed, and what is justified for users. Phantom Fudge has an implemented native preview and recorded local results; it does not have a qualified public release or an implemented Azure answer feature. A plausible design, passing synthetic test, and owner acceptance answer different questions. Combining them into one “done” badge would discard the most important information.
